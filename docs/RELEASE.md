# Подготовка выпуска

Код не опубликован автоматически. Первый выпуск — в отдельный тестовый Firebase-проект и preview frontend. Это позволяет проверить реальные задержки, не нарушая работу старой схемы `sessions`.

## Что подготовлено

- Функция `pulsar`, Node.js 22, регион `europe-west1`.
- Firestore rules и описание индексов.
- Вход по email/паролю, восстановление пароля, анонимный вход участников.
- SPA-маршруты `/`, `/participant`, `/projector`.
- Локальные проверки на эмуляторах, браузерные сценарии и нагрузочный скрипт.

## Облачный тестовый стенд

1. Выбрать Firebase-проект для тестового стенда. Проверить, что для него доступны Cloud Functions и Firestore, а также необходимый тариф/биллинг. Настройку биллинга не менять автоматически.
2. В Authentication включить Email/Password и Anonymous. Проверить домен тестового frontend в Authorized domains, письмо восстановления и возможность входа с другого устройства.
3. Сохранить действующие правила и сведения о существующих приложениях перед любыми изменениями в общем проекте. `firestore.rules` закрывает старую схему `sessions`; в работающий проект прототипа его отдельно от frontend не публиковать.
4. После одобрения публикации применить backend к выбранному тестовому проекту:

```sh
npx firebase deploy --project YOUR_STAGING_PROJECT --only functions:pulsar,firestore:rules,firestore:indexes
```

Личные снимки `rounds/{rid}/private/{uid}` требуют новой функции и правил до включения нового frontend. При повторном входе сервер восстанавливает отсутствующий снимок старого раунда.

5. Настроить Vercel preview с публичными `VITE_FIREBASE_*` именно тестового проекта, `VITE_USE_EMULATORS=false`; собрать `npm run build`, публиковать `dist`.
6. Проверить фактический опубликованный bundle: он не должен содержать включённые подключения к localhost-эмуляторам. Проверить HTTP-ответ, вход, создание встречи, отправку с телефона, закрытие, раскрытие, проектор и восстановление пароля.
7. Повторить нагрузочные измерения на отдельном согласованном облачном стенде. Текущий `test:load` намеренно привязан к локальным эмуляторам и сам в облако не переключается. Облачный генератор запускается отдельно, с ограничением 100 клиентов и очисткой тестовых данных.
8. Пройти ручной пилот и проверки в `VALIDATION.md`. Только после этого решать о production.

## Откат

Сохранить предыдущий frontend deployment и прежние правила. Откатывать frontend и совместимые с ним правила согласованно. Данные новой схемы не удалять при откате. Восстановление старого интерфейса не переносит новые встречи в `sessions`.

## Неподтверждённые внешние условия

Действующие облачные правила, включённые Auth providers, настройки почты, лимиты проекта, реальная задержка, Safari/iPhone/Android и Wi-Fi площадки требуют проверки. Локальный успешный тест не подтверждает ни одно из этих условий.
