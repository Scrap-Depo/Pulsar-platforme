# Проверки 2026-10-02

## Вывод

Функциональная реализация проверяется локально. Готовность к мероприятию на 100 реальных телефонах **не подтверждена**. Критерий PULSAR-014 по скорости пока не выполнен: часть измерений через API превышает 2 секунды. Production не изменялся.

Повторная диагностика: скрытый сбор на контрольном сервере ускорен до P95 0,196–0,232 с; немедленный показ на 100 клиентов остаётся непринятым. Подробности, условия и отчёты: [PERFORMANCE.md](PERFORMANCE.md). Таблица ниже сохраняет исходные измерения до оптимизации.

## Удаление фиксации проектора

Текущая версия не использует сохранённые снимки `rooms.frozen`. Пройдено 12 модульных, 10 интеграционных и 8 браузерных сценариев. Дополнительный браузерный сценарий записывает снимок старого вопроса в локальный эмулятор и проверяет, что предпросмотр ведущего и проектор после перезагрузки продолжают показывать текущий вопрос. Проверены очистка старого снимка при запуске и невозможность включить фиксацию командой старого клиента. Сборка проходит; сохраняется предупреждение Vite о размере пакета. Облачная публикация этой правки не выполнялась. Упоминания заморозки ниже описывают проверки предыдущей версии.

## Среда

macOS ARM64, Node 24.14.0 на машине проверки (production runtime задан Node 22), Java 21 во временной директории. Официальные эмуляторы Firebase Auth, Firestore и Functions, проект `demo-pulsar`. Интерфейс Vite на 127.0.0.1:5188. Chrome в независимых контекстах с мобильными размерами 390×844 и 360×740. Это не реальные iPhone, Android или Safari.

## Автоматические проверки

- TypeScript и Vite production build проходят.
- 4 модульных теста: диапазоны, длина Unicode, стабильные ID, публичные поля без идентичности.
- 6 интеграционных сценариев прошли и проверяют реальные Security Rules на Firestore emulator: изоляция владельцев, запрет прямой записи, доступ только к своему ответу, запрет чтения закрытых результатов, одобрение и повторную проверку, заморозку, лайки, историю, завершение, экспорт и рекурсивное удаление. Новый сценарий проверяет личный документ: запрет чужого чтения и прямой записи, одновременное сохранение трёх карточек, модерацию, обновление, восстановление для старого раунда и удаление.
- Нагрузочная проверка сервиса: 100 участников и 100 одновременно начатых отправок для каждого из четырёх типов. Сохранено ровно 100 документов от 100 разных участников; публикация содержит ровно 100 ответов. Это вызовы серверного сервиса непосредственно, не end-to-end задержка.
- 2 браузерных сценария прошли в Chrome: ведущий, два участника, проектор; черновик не теряется после чужого ответа и перезагрузки; закрытые ответы не отображаются; модерация; заморозка сохраняется после перезагрузки проектора; шкала без предвыбранного значения; потеря связи; завершение и выгрузка. Дополнительно проверены сохранение редактора, изменение голоса без дублирования, неизменность эфирной формулировки, лимит облака, повторная модерация изменённого слова, повторный вход ведущего, удаление встречи и исправление неверного кода.

## Нагрузка через API и живые подписки

100 независимых SDK-клиентов с отдельными Firebase Auth идентичностями. Все подключены к данным встречи. Регистрация выполнялась последовательно, отправка — одновременным пакетом. Для каждой формы создан отдельный раунд. 100 браузерных процессов и одновременный вход 100 человек этой проверкой не моделировались.

В каждом режиме сохранены и доставлены все 100 ответов во всех четырёх раундах. Потерь не обнаружено. Числа ниже — локальные измерения, не прогноз облачной производительности.

| Тип | P95 подтверждения, немедленный показ | P95 подтверждения, скрытый сбор | Раскрытие для 95% клиентов после закрытия |
| --- | ---: | ---: | ---: |
| Голосование | 19,614 с | 10,948 с | 0,748 с |
| Открытые ответы | 13,695 с | 5,307 с | 0,707 с |
| Шкала | 12,109 с | 1,056 с | 0,751 с |
| Облако | 11,995 с | 5,646 с | 0,730 с |

В режиме немедленного показа все 100 ответов стали видны 95% клиентов через 20–40 секунд от начала пакета отправок. Это серьёзное отклонение от целевого требования; режим нельзя считать принятым для 100 человек.

Задержка раскрытия скрытого сбора измерена от команды раскрытия, включая подписку и получение 100 опубликованных документов. Для немедленного режима интервал измеряется от начала пакета отправок до получения всего набора; это разные интервалы, их нельзя напрямую сравнивать как один показатель.

Исходные результаты: [SDK немедленный показ](validation/sdk-live.json), [SDK скрытый сбор](validation/sdk-hidden.json), [серверный сервис](validation/service-load.json).

Эмулятор Functions создаёт отдельные рабочие процессы для параллельных запросов; нагрузка на одну локальную машину отличается от облачной. Это возможный вклад в задержку, а не доказательство отсутствия проблемы в production. Требуется отдельный облачный тест с измерением холодного/прогретого запуска, времени функции и доставки подписки.

## Ручная приёмка перед мероприятием

- [ ] В тестовом облачном проекте опубликованы и повторно проверены реальные правила и функция.
- [ ] Email/Password и Anonymous работают; восстановление пароля приходит на реальную почту; ведущий восстанавливает доступ на другом устройстве.
- [ ] Повторён API/браузерный замер для 100 клиентов в облаке: P95 подтверждения <=2 с, доставка разрешённого результата <=3 с.
- [ ] Проверен всплеск одновременных подключений по QR-коду.
- [ ] Пройдены реальные iPhone/Safari и Android/Chrome, блокировка экрана и возвращение, переключение Wi-Fi/мобильной сети.
- [ ] Проведён пилот на 10–15 людях: >=90% входят и отвечают за минуту после общей инструкции.
- [ ] Ведущий проводит встречу без помощи разработчика и успевает модерировать ответы.
- [ ] Проверены проектор и Wi-Fi конкретной площадки, подготовлен запасной устный сценарий.

## Зависимости и публикация

После исправлений runtime-зависимости frontend и Functions не имеют известных уязвимостей по `npm audit --omit=dev` на дату проверки. В инструментах разработки остаются предупреждения npm audit; они не включены в production runtime. Нельзя приравнивать отсутствие предупреждений audit к полному аудиту безопасности.

Правила новой схемы закрывают доступ к старой `sessions`. Применение их отдельно к проекту работающего прототипа нарушит его доступ. Порядок безопасного тестового выпуска — [RELEASE.md](RELEASE.md).
