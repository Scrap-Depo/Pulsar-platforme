# Диагностика задержек — 2026-10-02

## Исправление

Участник подписывался на запрос к общей `responses` с фильтром по UID. При 100 таких подписках локальный Firestore существенно задерживал отправку и доставку. Теперь участник слушает адресный документ `rounds/{rid}/private/{uid}` с максимум тремя своими ответами. Сервер записывает его атомарно с исходным ответом и обновляет при модерации. История остаётся в исходной коллекции; чужие данные недоступны. Для ранее созданного раунда отсутствующий личный документ восстанавливается при повторном входе.

Четыре последовательных чтения при отправке объединены в `transaction.getAll`. Проверки участия, версии, этапа и завершения остались в транзакции. Для нового неопубликованного ответа убрано удаление отсутствующей публикации. Сервер журналирует длительность транзакции, чтения и число попыток без UID и текста ответов.

Цена изменения: дополнительный документ на участника/раунд и одна запись при отправке или модерации. Удаление встречи удаляет и эти документы. Экспорт читает исходные ответы, поэтому дублей нет.

## Проверка причин

Один и тот же callable проверен через Functions emulator (5001) и официальный Functions Framework (5002). Контрольный сервер исполняет **ту же функцию с проверкой Auth** в одном процессе с параллельными запросами. Firestore, Auth, Security Rules и клиентские подписки в обоих случаях — локальные эмуляторы/SDK, не заглушки. Это не модель облачного масштабирования или сети.

Эмулятор создал 50 рабочих процессов; P95 первого раунда составил 14,624 с. Исходный код в одном процессе всё равно дал P95 8,779–11,462 с в немедленном режиме. Значит, списывать всё на холодный запуск было неверно.

После объединения чтений контроль с одним публичным зрителем и 100 личными запросными подписками дал P95 4,420 с. Отключение только личных подписок снизило его до 0,214 с. Это диагностический контроль, не рабочий режим приложения. Замена запросных подписок адресными устранила это узкое место в скрытом сборе.

## Повторный результат скрытого сбора

100 отдельных Auth/SDK-клиентов, постоянные подписки на встречу и личные ответы, подписка ведущего на все ответы. После закрытия и раскрытия все клиенты получают все 100 результатов. Четыре типа, два прохода: **800 подтверждённых и доставленных ответов без потерь**.

Это **контрольный сервер Functions Framework**, после подключения клиентов. Холодный запуск, одновременный вход по QR, React-отрисовка, телефоны и интернет не включены. Числа не доказывают производственную готовность.

До изменения личных подписок в аналогичном скрытом режиме P95 составлял 3,875–4,540 с. ## Обычный Functions emulator

Итоговый прогон через 5001 также подтвердил и доставил все 800 ответов. Первый одновременный всплеск дал P95 5,808 с; следующие семь раундов — 0,289–0,593 с. Раскрытие для 95% клиентов — 0,782–0,835 с. Первый всплеск не проходит целевые 2 с, поэтому весь прогон не считается принятым по скорости. ## Оставшееся ограничение

Немедленный показ всем 100 участникам остаётся непринятым. После исправления личных подписок 100 записей сохранились, но часть слушателей не получила обновление за 120 секунд. Проверка Admin SDK подтвердила сохранение исходных и личных ответов. Запись в базе не равнозначна доставке на экран.

Пробная группировка публичных результатов в 16 документов и адресные подписки на них проблему не устранили; появились повторные попытки транзакций. Эксперимент **не включён** в итоговый код. Наблюдения указывают на проблему обработки подписок под нагрузкой локально, но не доказывают ни наличие, ни отсутствие той же проблемы в облаке.

PULSAR-014 остаётся открытой. Нужен замер на отдельном облачном стенде с холодным/прогретым запуском, затем реальные телефоны. Постоянно прогретые платные экземпляры не включались; production не менялся.

## Воспроизведение

Запустить три эмулятора по README, затем в отдельном терминале:

```sh
npm run dev:load-server
```

Контрольный сервер слушает только `127.0.0.1:5002`, принудительно использует `demo-pulsar` и локальные Auth/Firestore. Проверка:

```sh
PULSAR_FUNCTION_PORT=5002 PULSAR_LOAD_MODE=hidden PULSAR_LOAD_REPEATS=2 PULSAR_LOAD_ASSERT_BUDGET=true npm run test:load
```

Без `PULSAR_FUNCTION_PORT` используется Functions emulator (5001). Без `PULSAR_LOAD_MODE=hidden` проверяется немедленный показ, который пока не проходит приёмку. `PULSAR_LOAD_OUTPUT` задаёт путь JSON. `PULSAR_LOAD_ASSERT_BUDGET=true` возвращает ошибку при P95 подтверждения >2 с или доставки >3 с. По умолчанию медленный, но полностью доставленный прогон сохраняет измерения без утверждения о прохождении скорости.

Диагностика: `PULSAR_LOAD_PRIVATE_MODE=query` — старая личная подписка; `PULSAR_LOAD_OBSERVERS=1` — один зритель; `PULSAR_LOAD_PRIVATE_LISTENERS=false` — без личных подписок; `PULSAR_LOAD_TYPE=multiple-choice` — один тип. Сокращённые режимы не являются приёмкой полного приложения.
